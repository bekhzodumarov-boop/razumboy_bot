## Production — только после отдельного подтверждения владельца

### До merge и deployment

1. Зафиксировать текущий production deployment/коммит, ссылку нового Draft PR, выбранный runtime SHA, worker=1, Volume `/data`, фактический `DB_PATH=/data/razumboy.db`. Значения токенов и ADMIN_IDS не публиковать. Проверить связь Railway с веткой main: merge может сразу запустить deployment.
2. Проверить существование и ненулевой размер рабочей SQLite, открыть через `Path(path).resolve().as_uri() + '?mode=ro'`, выполнить `PRAGMA quick_check`. Не создавать для проверки объект Database: исходный конструктор может восстановить исторические записи в пустую БД. Отсутствующий/неверный Volume или путь — причина остановить релиз.
3. Создать новый уникальный backup бизнес-БД через SQLite Backup API (`source.backup(destination)`), source — mode=ro. Аналогично сохранить аналитический журнал, если он есть. Не копировать живой `.db` обычным файловым копированием: часть записей может быть в WAL. Две базы снимаются последовательно, это не общий атомарный снимок.
4. Для копий проверить `PRAGMA integrity_check`, размер и SHA256; сохранить защищённую копию вне Volume и проверить восстановление **в новый временный путь**. Не добавлять базы/содержимое в Git или PR. Проверку backup сначала отрепетировать на синтетической SQLite.
5. Записать агрегаты на момент снимка: игры, количество заявок по event_id/status, суммы team_size, максимальный registration_id; аналогично наличие профилей, подписок и подтверждений. Для проверки сохранности конкретных существующих заявок можно сравнить локальные хеши строк по ID, не выводя персональные поля в логи. Отдельно учесть заявки/отмены, появившиеся после снимка.
6. Убедиться, что финальные тесты/staging успешны, diff содержит только согласованный состав, чужие локальные файлы отсутствуют. Перед подтверждённым merge сохранить известный исправный артефакт для отката.

1. После разрешения владельца выполнить merge/выкладку выбранного кода одной репликой. Сохранить `ADMIN_DIGEST_ENABLED=0`; рабочий `SCHEDULER_ENABLED=1` оставляет семь прежних заданий. Не переносить staging ADMIN_IDS/токен/DB_PATH в production.
2. Проверить Railway SUCCESS, стабильный polling, отсутствие циклических перезапусков, один worker, доступность Volume. Изолированно проверить состав планировщика, не запускать вручную рабочие рассылки. Сверить агрегаты и существующие заявки с backup с учётом легитимных изменений за время релиза; статус/данные заявок не должны самопроизвольно измениться.

В разрешённом тестовом аккаунте проверить `/start`, существующий профиль, запрос номера/отклонение чужого контакта, свою тестовую регистрацию, продолжение, перезапуск, отмену, повторное подтверждение и «Мои регистрации». Создание/отмена тестовой заявки в production требует того же отдельного подтверждения, как и любое изменение рабочей БД. До него ограничиться чтением админ-панели и `/report 50`.

5. Включение `ADMIN_DIGEST_ENABLED=1` — отдельное согласованное действие после проверки получателей. После разрешённого включения убедиться в 8 задачах, следующем запуске 09:00 Asia/Tashkent и отсутствии дублей. При нескольких репликах включать нельзя без распределённой защиты.

### Откат

При ошибке сначала отключить только новый ежедневный отчёт (`ADMIN_DIGEST_ENABLED=0`). При проблемах кода вернуть предыдущий исправный deployment/коммит, сохранив текущие DB_PATH и Volume. Новых миграций в этом релизе нет. Не восстанавливать старую SQLite поверх текущей: это удалит новые заявки/отмены. Если обнаружено повреждение данных, приостановить изменяющие операции, снять новый snapshot и разбирать восстановление отдельно с владельцем, сохраняя все новые записи.

## Оставшиеся ограничения

- MemoryStorage не переживает рестарт: старый черновик нельзя надёжно восстановить из обезличенной аналитики. Подтверждённые заявки сохраняются в SQLite.
- Изоляция FSM и защита от дублей рассчитаны на один worker; распределённой уникальности/ежедневного exactly-once нет. Пропущенный во время остановки digest не досылается.
- Журнал читается целиком; при значительном росте нужны дополнительные меры производительности. Ручной ввод номера не подтверждает владение им.
- Заявки/заявленные игроки не равны посещению/оплатам; источник ссылки не является доказанной рекламной атрибуцией.
- Документы admin-digest-validation.md и subscriber-phone-ux.md содержат результаты исходных PR; результаты этой интеграции фиксируются отдельно.
