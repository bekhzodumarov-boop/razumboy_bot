# Явка, оплаты и расходы по игре

Основа PR #10 — production `f479a249165d9ce68f0a57d841f65f91a1fef9a5`. Эта доработка сначала выпускается только на @Razumboy_Test_Bot. Production остается закреплен на прежнем коммите до отдельного разрешения.

## Сценарий администратора

1. В личном чате: **👥 Явка** или `/attendance` → выбрать игру, в том числе прошедшую.
2. Бот предлагает **70 тыс.**, **100 тыс.**, **Другая сумма**. Это цена за одного человека. Для другой цены ввести полную положительную целую сумму в сумах, например `85000`. Цена сохраняется сразу, без дополнительного подтверждения; появляется список команд. Повторное открытие игры из списка снова предлагает цену. Сохраненные оплаты при изменении цены не пересчитываются.
3. Выбрать команду и отправить одним сообщением:

   ```text
   Узум 2
   Клик 4
   Итого 6
   ```

4. Бот показывает расчет по всем пяти способам, включая нулевые:

   ```text
   Итоги оплат по способам (каждый игрок учитывается один раз):
   Uzum: 2 чел. / 140 000 сум
   Payme: 0 чел. / 0 сум
   Click: 4 чел. / 280 000 сум
   Перевод на карту: 0 чел. / 0 сум
   Наличные: 0 чел. / 0 сум

   Итого: 6 чел. / 420 000 сум
   ```

   Под расчетом только **✅ Подтвердить** и **Отмена**. До подтверждения оплаты не записаны. Можно отправить исправленный текст: прежняя кнопка станет недействительной. Даже некорректное исправление отзывает предыдущую кнопку. При отмене, ошибке или потере черновика сохраненные оплаты остаются прежними.
5. Одно подтверждение атомарно заменяет ВСЮ прежнюю разбивку команды. Неуказанные способы равны нулю. Повторное подтверждение не создает новую операцию. После сохранения актуальная карточка и кнопки **Следующая команда**, **К списку команд**, **Итоги игры** появляются внизу чата.
6. Поддерживаются Узум/Uzum, Пейми/Payme, Клик/Click, перевод на карту, наличные; также прежние варианты написания и сокращения. Строка «Итого» необязательна, но должна совпадать с суммой игроков. Ошибки указывают проблемную строку, например «В строке “Пейми” не указано количество».
7. Все суммы оплат рассчитываются по цене игры. Произвольные суммы строк, скидки формата `Узум 2 = 130000` и прежний пошаговый ввод больше не доступны. Кнопки отдельных способов удалены, исторические callback-кнопки отклоняются.
8. Фактическая явка и оплата — отдельные показатели. Ввод оплаты разрешен без отметки явки, неизвестная явка остается неизвестной. Если явка отмечена, оплативших не может быть больше пришедших. Явку можно указать отдельной кнопкой и сохранить с подтверждением. Уменьшение явки ниже уже оплаченного количества отклоняется. Исходные заявки не меняются.

## Остальные функции

Сохраняются гости без заявки, расходы и произвольные статьи, распределение прибыли соучредителям, финансовый отчет и CSV. Выплата Фарруху остается распределением прибыли, а не расходом. Пустые статьи — неизвестные расходы, их нужно заполнить или исключить. Результат по неполным данным не является окончательной прибылью.

Старый `/report` остается отчетом регистрационной воронки. Регистрация, рассылки и семь прежних задач планировщика не меняются; ежедневная сводка включается только своим флагом.

## Хранение и конкурентные изменения

Пять отдельных `finance_*` таблиц. Подтверждение разбивки использует `BEGIN IMMEDIATE`, проверяет ревизии команды и цены и пишет одну запись аудита с уникальным ключом. Предварительный расчет использует SQL read snapshot без записи оплат. Если другой администратор изменил цену, явку или оплаты, старое подтверждение не перезаписывает его изменения: нужно открыть карточку заново. Цена выбирается с ревизией и одноразовой кнопкой.

Доступ только ADMIN_IDS в личном чате. Нет платежных API, банковской проверки, автоматических списаний или новых задач планировщика. Черновики FSM теряются при рестарте; подтвержденные данные остаются в SQLite. CSV защищает произвольные названия от формул.

## Изолированный пользовательский тест

- Railway: supportive-grace / staging, запуск `python finance_preview.py`.
- Только @Razumboy_Test_Bot; guard проверяет окружение, имя бота и точный новый путь `/data/razumboy-finance-preview-v2.sqlite`.
- Старая preview-БД и ее оплаты не используются и не перезаписываются. Новая БД содержит только вымышленные команды, неизвестную явку и оплаты.
- `SCHEDULER_ENABLED=0`, `ADMIN_DIGEST_ENABLED=0`, `CHANNEL_ID=0`; preview не запускает планировщик и рассылки.
- Открыть `/start` → **👥 Явка** → игра → **70 тыс.** → команда → сообщение выше → проверить **420 000 сум** → подтвердить → **Итоги игры**.
- Проверить исправление текста до подтверждения, отмену, нулевые способы, другую цену и отдельную явку.
- **Новый тест** / `/newdemo` создает новую синтетическую игру, сохраняя старые попытки.

## Production

Эта задача не разрешает production-деплой. Для будущего выпуска требуются отдельное разрешение, свежие SQLite Backup API копии обеих БД вне Railway с SHA256/integrity_check, сверка pinned SHA и конфигурации. Сохранить `/data/razumboy.db`, переменные, один worker и `python app.py`. Не переносить preview-данные.

Откат — вернуть прежний код с текущей базой, не восстанавливать старую SQLite поверх новых регистраций и оплат. Мост/веб-дашборд другими PR не подключаются этим изменением.
