# Аудит хранения подписчиков RAZUMBOY

Дата: 20 октября 2026. Ветка `codex/subscriber-storage-audit` создана от
`codex/registration-funnel-analytics` после коммита `c6b869d`. `main` не менялся.
Аудит выполнен по исходному коду; production и реальные резервные копии не читались.
Реальная локальная копия для анализа не предоставлена. Все численные проверки
и пример отчёта основаны только на синтетических тестовых данных.

## 1. Связи и источники данных

| Таблица | Идентификация/связи | Содержание и ограничения |
|---|---|---|
| `users` | Внутренний `id`, уникальный `telegram_id` | Создаётся/обновляется через `/start`; телефон здесь не синхронизируется с анкетой/заявкой |
| `subscribers_profile` | Уникальный `telegram_id`, связь с `users.telegram_id` | Профиль подписчика: сейчас имя и телефон, исторические поля остаются |
| `registrations` | `user_id` ссылается на `users.id`, не на Telegram ID | Заявки команды: собственные контактные данные капитана, дата создания и текущий статус |
| `referrals` | Реферер и приглашённый связаны через Telegram ID | Реферальная связь; `qualified=1` означает заполнение анкеты, не оплату и не посещение |

Полноценной сущности «человек»/«капитан» с проверенной идентичностью нет. Скрипт
считает капитанов как аккаунты владельцев заявок. Телефон/имя капитана могут
принадлежать другому человеку; общий телефон не является основанием склеивать аккаунты.
`team_size` не позволяет получить контакты всех игроков.

`Database._connect()` не включает `PRAGMA foreign_keys=ON`. Объявленные FK сами
по себе не гарантируют целостность всех записей. Скрипт отдельно считает анкеты,
заявки и стороны реферальных связей без соответствующего пользователя.

## 2. Проверка подписки и согласий

Найдены следующие особенности кода:

1. `users.subscribed` по умолчанию равен `1`; `upsert_user()` создаёт новых
   пользователей уже подписанными.
2. Обработчик `/start` без отдельного выбора пользователя вызывает
   `set_subscription(..., True)`.
3. `subscribe_start()` включает подписку **до** завершения анкеты.
4. `Database._migrate()` при каждом создании `Database` выполняет
   `UPDATE users SET subscribed=1 WHERE subscribed=0`. Это стирает состояние
   отписки при перезапуске. В текущей задаче поведение не изменено.
5. В исследованных обработчиках нет пользовательской команды отписки и нет
   вызова `set_subscription(..., False)`.
6. У флага нет времени изменения, версии согласия, источника, журнала отзыва.
   `subscribed=1` не подтверждает ни доставляемость сообщений, ни активность.
7. CSV использует `get_all_subscriber_profiles()` без фильтра `subscribed`:
   анкеты и подписанные пользователи — разные множества. Число в меню подписчиков
   и количество профилей в CSV могут закономерно отличаться.
8. В схеме и обработчиках не обнаружены отдельное согласие на рекламную передачу
   Meta, текст/версия такого согласия и доказательство его получения/отзыва.
   Вне бота может существовать отдельный реестр — его наличие не проверялось.

Итог: **нельзя использовать `subscribed`, заполнение анкеты, заявку или реферал
как подтверждение разрешения на Meta Custom Audiences**. Скрипт всегда возвращает
`evidence_verified=false` и `not_verified_do_not_export`. Даже найденное название
колонки `consent` лишь увеличивает счётчик подсказок схемы и не разрешает загрузку.

Рекомендуемые отдельные изменения после согласования: убрать повторное включение
подписки миграцией, добавить явную отписку, разделить сервисные уведомления и
маркетинг, вести журнал согласий по конкретной цели с временем, версией текста,
каналом получения, правовым основанием и отзывом. Не включать пользователей задним
числом и не проставлять согласия массово на основании старого `subscribed`.

## 3. Безопасный скрипт

`subscriber_audit.py` использует только стандартную библиотеку. Пример запуска
на заранее подготовленном **автономном offline snapshot**:

```powershell
python subscriber_audit.py "C:\Backups\offline-copy.sqlite" --confirm-local-backup --as-of "2026-10-21T00:00:00+05:00"
```

Без `--as-of` используется текущий UTC. Явно указанное время требует часовой пояс.
Параметр задаёт конец окон активности; общие количества и текущие статусы относятся
к состоянию предоставленного backup, а не реконструируются на историческую дату.

Скрипт:

- не ищет БД автоматически, не читает `.env`, не создаёт объект `Database`;
- требует подтверждение локального backup, отказывается от URL/UNC, отсутствующего
  файла, стандартного `razumboy.db` рядом со скриптом и файлов под `/data`;
- отказывается от snapshot с `-wal`, `-shm`, `-journal`: нельзя игнорировать
  незавершённые данные live SQLite;
- открывает `mode=ro&immutable=1`, включает `query_only` и отключает доверие схеме;
- принимает только ожидаемые физические таблицы и поля, без выполнения миграций;
- не запрашивает имена/комментарии и не выводит исходные телефоны, идентификаторы,
  пути файлов, содержимое исключений или названия произвольных полей из БД;
- не создаёт списки, хешированные идентификаторы, CSV-аудитории и не обращается к Meta.

Флаг подтверждения — обязательство оператора выбрать именно копию. Технически
невозможно распознать любую live-БД по произвольному имени; не указывать путь
к рабочему файлу. `immutable=1` рассчитан только на неизменяемый snapshot.
Snapshot следует получить SQLite Backup API и хранить с ограниченным доступом.
Сам факт агрегирования не делает исходную БД публичной или обезличенной.

## 4. Метрики и трактовка

- Количество строк четырёх таблиц.
- Подписка `1`, `0`, некорректные/NULL значения; подписанные без анкеты,
  анкеты пользователей с флагом `0`.
- Для трёх источников телефонов: пустые, неподдерживаемые/некорректные,
  структурно корректные строки, уникальные номера и повторные строки;
  общая уникальная сумма и попарные пересечения номеров.
- Попарные пересечения таблиц по аккаунтам, тройное пересечение
  users/profiles/registrations; реферальное множество включает обе стороны связи.
- Капитаны с 1, 2, 3+ заявками: отдельно все строки и только текущий `confirmed`.
  Это не число посещённых/оплаченных игр. Отмена и повторная запись могут увеличить
  число строк; дубли `confirmed` на одну игру считаются отдельно как аномалия.
- Связи без пользователя, различающиеся телефоны в анкетах/заявках одного аккаунта,
  один телефон у разных аккаунтов и саморефералы. Различие телефонов может быть
  легитимным, поэтому данные не исправляются автоматически.
- Активность за последние 90/180 дней: новые пользователи, анкеты, заявки и
  реферальные связи; уникальные аккаунты с заявками, в том числе `confirmed`;
  неадминистративные капитаны с `confirmed` и корректным телефоном;
  объединение аккаунтов с наблюдаемым созданием записей.

Номер считается структурно корректным для Узбекистана: код страны и девять ASCII
цифр; пробелы, скобки, дефисы нормализуются, отсутствие `+` перед кодом допускается.
Пустой национальный номер из нулей исключается. Местным девятизначным номерам
страна автоматически не присваивается; иностранные номера помечаются как
неподдерживаемые. Это не проверка оператора, SMS, актуальности или принадлежности.

Окна активности — `[as_of - N дней, as_of)`. Стандартные SQLite-времена без
часового пояса трактуются как UTC; значения с offset приводятся к UTC.
Некорректные/пустые даты считаются отдельно. `referrals.qualified_at` исключён
из активности: код заполняет его через локальный `datetime.now()`, не фиксируя
часовой пояс. Создание связи учитывается как действие приглашённого, а не реферера.

Профиль обновляется через UPSERT без изменения `created_at`; у `users` нет
`last_seen`, повторные `/start` здесь не датируются. Изменение/отмена заявки
также не имеет полной истории. Поэтому эти окна **не равны DAU/MAU и не доказывают
неактивность остальных**. Отдельный журнал воронки не открывается скриптом.

Пример с полностью синтетическими агрегатами:
[`subscriber-audit-example.json`](subscriber-audit-example.json).

## 5. Потенциальные рекламные сегменты — только оценка

| Сегмент | Потенциал после правовой проверки | Ограничения |
|---|---|---|
| Неадминистративные капитаны с корректным телефоном и 1+ `confirmed` | Возврат участников | Контакт капитана может не принадлежать владельцу аккаунта; нет доказательства посещения |
| Капитаны с 2+/3+ `confirmed` | Повторные команды, потенциальное ядро | Повторные заявки не означают оплату или пожизненную ценность |
| Капитаны с заявкой за 90/180 дней | Недавний интерес | Дата заявки, не последнее посещение бота; сегменты пересекаются |
| Профили с телефоном, без `confirmed` | Потенциальные лиды | Заполнение анкеты не разрешает передачу третьей стороне |
| Квалифицированные приглашённые с профилем | Реферальные лиды | Квалификация относится к анкете, а не к согласию на рекламу |
| Только Telegram-аккаунт без подходящего контакта | Недостаточно данных для телефонного сопоставления | Telegram ID не является Facebook/App User ID |

Скрипт считает только размеры сегментов, не их состав. Администраторы исключены
из потенциальных сегментов. Отписавшиеся и пользователи без подтверждённого
правового основания не должны автоматически попадать в рекламную аудиторию;
размеры сегментов не являются числом юридически допущенных контактов.

До любых списков требуется проверить цель сбора, разрешение на рекламное
сопоставление/передачу Meta, механизм отзыва и удаления из аудиторий, актуальность
контакта и принадлежность, применимые ограничения по возрасту, трансграничной
передаче и хранению. Хеширование номера не заменяет эти проверки.

Источники для правовой проверки (проверено 20 октября 2026):

- [Условия Meta Customer List Custom Audiences](https://www.facebook.com/legal/terms/customaudience/update):
  индексированная официальная выдержка требует необходимых прав, разрешений и
  законного основания. Полный текст при открытии перенаправлял на вход; перед
  практическим решением проверить актуальные условия из авторизованного кабинета.
- [Закон Узбекистана «О персональных данных»](https://lex.uz/ru/docs/4396428):
  для проверки важны условия обработки, подтверждаемость согласия (ст. 21),
  трансграничная передача (ст. 15) и условия хранения/обработки (ст. 27¹).
  Применимость и достаточность основания для Meta нужно определить отдельно.

В этой задаче законные основания конкретных контактов не установлены и
рекламные аудитории не созданы.

## 6. CSV и проверка

В `handlers/admin.py::subs_export_csv` `sqlite3.Row.get('username')` заменён
на доступ `p['username']`. SELECT уже возвращает эту колонку через LEFT JOIN,
в том числе NULL для отсутствующего пользователя/username. Состав CSV и
проверка администраторских прав сохранены. Экспорт не вызывался с реальными данными.

Это точечный ремонт старого экспорта, не рекламный экспорт. Существующее ручное
формирование CSV имеет отдельные ограничения экранирования кавычек/переносов;
переработка формата и фильтрации подписки не входит в исправление `.get()`.

Тесты проверяют реальные `sqlite3.Row` с username/NULL, запрет экспорта неадминистратору,
точные агрегаты, нормализацию, пересечения, окна дат, пустую БД, отсутствие утечек
в JSON/ошибках, отказ от live sidecars, ожидаемой рабочей БД и views, совпадение
SHA-256 до/после анализа, запрет UPDATE/CREATE, отсутствие создания отсутствующей БД
и отсутствие автоматического признания согласия по имени колонки.

Итог: **56 тестов — OK** на Python 3.13.16 и Python 3.12.14 (Windows),
в том числе 11 тестов аудита и 2 регрессионных теста CSV. Проверка синтаксиса
Python 3.13 и `git diff --check` пройдены. Реальные резервные копии не анализировались.

```powershell
python -m unittest discover -s tests -q
python -m py_compile subscriber_audit.py handlers/admin.py tests/test_subscriber_audit.py tests/test_subscriber_csv.py
```

Production не подключался, миграции и деплой не выполнялись. Подписки не изменялись.
