# RAZUMBOY — автоматический отчёт по играм

## Что добавлено
- Админ-кнопка **📈 Отчёт по играм** и команда `/report`.
- До 5 ближайших открытых игр, актуальные подтверждённые/отменённые заявки и сумма заявленных игроков из рабочей БД.
- Аналитика за последние 24 часа по отдельному журналу: запуски, отправки карточек, начала, завершения, незавершённые/отменённые/заменённые формы, шаги и источники.
- Только агрегаты. Никаких имён, телефонов, Telegram ID или списка незавершённых пользователей.
- Ежедневная отправка администраторам в 09:00 по Asia/Tashkent при `ADMIN_DIGEST_ENABLED=1`. По умолчанию **0**. Нужен действующий `SCHEDULER_ENABLED=1`.

## Ограничения
- Счётчики регистрации в окне 24 часа — активность, не когортная конверсия.
- `unfinished` означает открытую попытку, не доказанный отказ.
- Заявленные игроки ≠ оплатившие / пришедшие, источник ссылки ≠ доказанный канал.
- Расходы Meta Ads не подключены: отчёт не вычисляет CPC, CAC, ROAS или ROMI.
- Если аналитика недоступна, сводка заявок продолжит отображаться с предупреждением.
- Отправка осуществляется админ-ID из `ADMIN_IDS`. Перед включением проверить список получателей.
- Масштабирование: код читает журнал целиком; при больших объёмах потребуются индексы/инкрементальные агрегаты.

## Проверка staging
1. Использовать тестовый токен, тестовую БД и volume; `SCHEDULER_ENABLED=0`, `FUNNEL_ANALYTICS_ENABLED=1`, `ADMIN_DIGEST_ENABLED=0`.
2. Выполнить `python -m unittest discover -s tests -q`; подтвердить, что число задач в scheduler без опции равно 7, с опцией — 8.
3. Зайти в `@Razumboy_Test_Bot` как тестовый администратор и вызвать `/report`, затем кнопку. Проверить соответствие SQL-сводке без разглашения персональных данных.
4. Проверить отсутствие доступа у обычного пользователя и недоступность аналитического журнала без падения бота.
5. Для тестовой рассылки в staging можно временно выставить `ADMIN_DIGEST_ENABLED=1` и вызвать асинхронную функцию в контролируемом тесте, **но не копировать production ADMIN_IDS**.
6. Проверить форматирование большого количества игр и длину Telegram-сообщения (4096 символов). При росте разнести по сообщениям — в текущем MVP ограничено 5 играми.

## Выпуск
1. Сначала свежий SQLite backup API + локальный SHA256, как и при прошлом релизе.
2. PR направлен в main, значит merge может вызвать production auto-deploy. Не мерджить до независимого теста в staging.
3. Оставить `ADMIN_DIGEST_ENABLED=0` при первом production-релизе. Проверить, что polling, Scheduler и прежние 7 jobs работают. Проверить команду `/report`.
4. Сверить счётчики с админ-панелью и обезличенным SQL.
5. Проверить `ADMIN_IDS` и включить `ADMIN_DIGEST_ENABLED=1`. Контролируемое изменение переменной приведёт к перезапуску.
6. После включения запланирован ежедневный отчёт в 09:00 по Ташкенту.

## Откат
- Отключить `ADMIN_DIGEST_ENABLED=0`; ручной отчёт останется доступным.
- При сбое кода вернуть предыдущий deployment/commit **без восстановления старой базы поверх новых заявок**.
- Прежние задания APScheduler должны остаться включёнными.
