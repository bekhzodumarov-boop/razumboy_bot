# План тестирования, backup и выкладки аналитики

Этот документ — план будущих действий после отдельного разрешения владельца.
При доработке ветки production, Railway, рабочие секреты и рабочая БД не использовались.

## 1. Зафиксировать проверяемую версию

1. Проверить diff ветки `codex/registration-funnel-analytics` и записать SHA.
2. Убедиться, что `main` не менялся, личные локальные файлы не включены.
3. Перед любой выкладкой проверить конфигурацию автоматического деплоя Railway:
   публикация тестовой ветки не должна запускать production. Эту конфигурацию
   в текущей работе не проверяли и не меняли.
4. Записать SHA/артефакт текущего production, путь Volume, число worker,
   состояние `FUNNEL_ANALYTICS_ENABLED` и `SCHEDULER_ENABLED`. Не копировать значения секретов в отчёт.

## 2. Повторить локальные проверки

В отдельном окружении с зависимостями `requirements.txt`:

```powershell
python -m unittest discover -s tests -v
python -m py_compile analytics.py analytics_report.py analytics_middleware.py scheduling.py app.py handlers/common.py handlers/registration.py
git diff --check
```

Критерии: 43 теста проходят, нет ошибок синтаксиса/whitespace. Тесты используют
только `TemporaryDirectory`, тестовую SQLite и OfflineSession/моки, не читают `.env`
и не вызывают `main()`. `create_dispatcher()` собирает те же роутеры без старта
планировщика, polling и инициализации бизнес-БД.

Локально пройдено по 43 теста на Python 3.12.14 и Python 3.13.16 (Windows),
`pip check` — без конфликтов. Для staging на Python 3.13 повторить этот набор
в целевом Linux-окружении до включения любого реального получателя.

Отдельно убедиться по тестам:

1. `event_50` и `event_50_src_instagram` открывают карточку; начало только по кнопке.
2. Ручной ввод, контакт и прошлые значения дают шаги одной попытки.
3. Повторные/одновременные кнопки не дают второй заявки.
4. Отмены, дубли, ошибки и незавершённые формы попадают в разные категории.
5. Ошибка затем успешное подтверждение считается завершением, а ошибка остаётся
   в счётчике инцидентов.
6. После перезапуска старый черновик не восстанавливается; журнал остаётся.
7. Неизвестный источник не сохраняется произвольной строкой.
8. При блокировке или недоступности журнала заявка сохраняется.
9. Исторический отчёт не использует события после `--until`.

## 3. Проверить резервное копирование на тестовых данных

Сначала отработать весь цикл на отдельной SQLite. Для работающей SQLite использовать
SQLite Backup API (`source.backup(destination)`), а не простое копирование `.db`:
актуальные данные могут находиться в WAL. Источник открывать по SQLite URI
с `mode=ro`; файл назначения — новый уникальный путь, чтобы не затереть backup.
Не создавать объект проектного `Database`: его конструктор запускает миграции.

1. Создать тестовые заявки и события, записать контрольные количества.
2. Сделать snapshot тестовой бизнес-БД и отдельно snapshot тестового журнала.
3. Для каждой копии открыть SQLite read-only, выполнить `PRAGMA integrity_check`;
   результат должен быть `ok`.
4. Восстановить копии **в новые тестовые пути**, проверить количества заявок,
   статусы и результаты отчёта. Не выполнять restore поверх исходников.
5. Сохранить размеры, SHA-256, время UTC и результаты проверки в журнал операции.
   Не публиковать содержимое бизнес-БД: оно содержит персональные данные.

## 4. Изолированная ручная проверка перед production

Проводить только после согласования отдельного staging-окружения. Использовать
отдельного тестового Telegram-бота, отдельные БД/Volume и тестовых получателей.
Рабочие chat ID, каналы и токен не переносить. До первого старта задать
`SCHEDULER_ENABLED=0`: объект APScheduler и все семь заданий не создаются.
Без переменной или с `=1` остаётся прежний production-режим. Другие значения
отклоняются до создания БД. Ручные рассылки, отложенное завершение вручную
запущенного блиц-квиза и уведомления о запуске/регистрации этим флагом не отключаются:
они должны иметь только тестовых получателей. Не запускать вторую копию
production-бота и не подключать staging к production Volume.

1. Выкатить согласованный SHA в staging с `SCHEDULER_ENABLED=0`, аналитика сначала выключена.
2. Проверить обычную регистрацию и отмену.
3. Включить аналитику в staging, проверить старую и размеченные ссылки.
4. Пройти полную форму, редактирование и повторное подтверждение; сверить заявку
   и события на безопасных копиях БД.
5. Перезапустить staging в середине формы, проверить старую кнопку и новую попытку.
6. Проверить недоступность журнала на staging; основная заявка должна сохраниться.
7. Получить отчёты по игре 50, датам с `+05:00` и источнику. Проверить границы суток.
8. Проверить штатную остановку staging и отсутствие сообщений планировщика.
   Режим `=1` проверять только на отдельном тестовом окружении с тестовыми
   получателями и заданиями, не на production.

Текущая серия автоматических тестов не заменяет этот ручной этап и не подтверждает
поведение сети Telegram, реального Volume или конфигурации Railway.

## 5. Backup перед разрешённой выкладкой

1. Выбрать окно минимальной активности; перезапуск теряет MemoryStorage.
2. Через согласованный канал администрирования сделать snapshot основной БД
   Backup API; если аналитика уже включена — отдельно snapshot её файла.
   Если файла ещё нет, зафиксировать это, а не создавать его ради backup.
3. Проверить integrity и восстановление копий на изолированном пути.
4. Сохранить backup вне контейнера/каталога будущего релиза в контролируемом
   хранилище с ограниченным доступом. Проверить, что backup доступен для отката.
5. Основная БД и журнал не имеют общей транзакции: два online snapshot не являются
   атомарной парой. Для точной сверки на время обоих snapshot остановить приём
   обновлений одним worker и согласовать краткое окно обслуживания.
6. Ещё раз проверить прежний `Database._migrate()`: при старте он выполняет
   существующие операции (в том числе подписки). Код аналитики их не изменяет.

## 6. Управляемая выкладка на Railway

1. Получить разрешение на конкретный SHA и окно. До этого не менять production.
2. Проверить закреплённую ветку, Volume `/data`, свободное место, права записи,
   одного worker и отсутствие параллельного polling старого/нового процесса.
   Для production сохранить `SCHEDULER_ENABLED=1` либо отсутствие переменной.
3. Развернуть SHA с `FUNNEL_ANALYTICS_ENABLED=0`, проверить готовность worker
   и одну согласованную тестовую регистрацию. Не выводить переменные окружения.
4. При успешной проверке и отдельном согласовании включить флаг `=1`, выполнить
   управляемый перезапуск. Только тогда создаётся/обновляется отдельный журнал.
   В старый журнал добавляется `source DEFAULT 'unknown'`, бизнес-схема не меняется.
5. Проверить Railway после каждого этапа: один живой worker, нет конфликтов polling,
   нет `analytics_init_failed`/массовых `analytics_write_failed`, заявки сохраняются.
6. Проверить размеченную тестовую ссылку и отчёт на snapshot журнала. Сверить
   завершения с заявками; отсутствие события не доказывает отсутствие заявки.
7. Наблюдать за размером Volume, задержками и ошибками. Установить срок хранения
   и процедуру удаления/архива; автоматической очистки пока нет.

## 7. Откат и критерии остановки

Остановить включение при потере заявок, повторных заявках, конфликте polling,
неработающем Volume или массовых ошибках. При проблеме только аналитики выставить
`FUNNEL_ANALYTICS_ENABLED=0` и управляемо перезапустить единственный worker.

Если проблема остаётся, развернуть прежний сохранённый SHA/артефакт и проверить
регистрацию и Railway. Добавленная колонка отдельного журнала совместима с прежним
кодом `f23d086`; удалять её или файл для отката не требуется. Бизнес-схема не менялась.

Не восстанавливать старую production БД поверх актуальной автоматически: это
потеряет новые заявки. Restore допустим только отдельным решением после сравнения
и переноса новых данных. Исходные файлы и snapshot сохранить до окончания разбора.

Оставшиеся ограничения: неатомарность двух БД, потеря черновиков и источника после
сброса FSM, один worker, линейное чтение истории отчётом, отсутствие автоматической
очистки. Источник ссылки можно переслать или подменить; это не доказательство
реального рекламного канала.
