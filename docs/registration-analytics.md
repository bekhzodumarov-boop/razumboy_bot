# Минимальная аналитика регистрации

Дата проверки: 20 октября 2026. Ветка: `codex/registration-funnel-analytics`.

## Реализация

По умолчанию аналитика выключена. При `FUNNEL_ANALYTICS_ENABLED=1` создаётся
отдельный SQLite-файл `<DB_PATH>.analytics.sqlite` рядом с основной БД.
При существующем пути `/data/razumboy.db` это `/data/razumboy.db.analytics.sqlite`.
Основные таблицы и методы миграции `database.py` не изменены.

Журнал содержит `timestamp` (UTC), `user_id` (Telegram ID аккаунта), `event_id`
(может быть NULL), `attempt_id` (может быть NULL вне формы), `event_name`,
`step`, `result`, `dedup_key`, `source`. Имена, телефоны, комментарии, тексты сообщений,
сырые Update и тексты исключений не записываются.
Идентификаторы аккаунтов всё равно требуют ограничения доступа к файлу.

События: `bot_started`, `event_card_sent`, `registration_started`,
`registration_step_completed`, `registration_cancelled`,
`registration_completed`, `registration_failed`.

`event_card_sent` означает успешную отправку карточки, а не прочтение.
`registration_step_completed` возникает при переходе после принятого ответа,
включая прежние значения и контакт. Ошибочный ввод не считается заполненным шагом.
Редактирование отмечается шагом `confirm` с результатом `edited`.
Отказы: `unavailable`, `duplicate`, `user_missing`, `state_lost`, `handler_error`.
Отмена: `cancelled`; замена начатой формы новой: `superseded`.

Ссылка `/start event_50` сохраняет прежний сценарий: карточка, затем отдельная
кнопка регистрации. Просмотр не создаёт попытку регистрации.

## Попытки и повторы

ID попытки детерминирован по аккаунту и идентификатору входного сообщения/callback,
ответы связаны через FSM. Повтор той же доставки начала не создаёт новую попытку,
в том числе после перезапуска, если запись начала сохранилась в журнале.
Повторное нажатие регистрации той же игры во время заполнения сохраняет форму.
Запуск новой формы из меню отдельным сообщением создаёт новую попытку, предыдущая
отмечается как заменённая. При смене игры также создаётся новая попытка.

Редактирование сохраняет ID попытки и увеличивает ревизию, чтобы повторное
заполнение шага было видно отдельно. Шаги дедуплицируются по попытке, ревизии,
событию, шагу и коду. Терминальное событие имеет единый ключ попытки.
`bot_started` дедуплицируется по chat/message ID, карточка из callback — по callback ID.
Разные запросы карточки считаются разными отправками.

Сериализация обновлений одного FSM-контекста через `SimpleEventIsolation`
предотвращает одновременную обработку двух подтверждений в одном процессе.
Это не замена ограничению уникальности заявок при нескольких worker.
Архитектура по-прежнему рассчитана на один процесс бота.

## Ошибки и перезапуск

Соединения журнала закрываются явно; ожидание SQLite-lock ограничено 0,1 с.
Ошибка создания/чтения/записи аналитики не прерывает регистрацию. В технический
лог попадает только постоянный код ошибки без параметров и текста исключения.
При ошибке инициализации сбор выключен до следующего запуска.

Сохранение заявки важнее аналитики: событие завершения записывается после
успешного `create_registration`, до отправки уведомлений. Между основной БД
и отдельным журналом нет общей транзакции. При сбое записи/падении процесса
успешная заявка может отсутствовать в аналитике. Автоматического восстановления
пропущенных событий нет; отчёт не является финансовым или операционным реестром.

FSM остаётся в памяти: после рестарта ответы не восстанавливаются. Журнал
сохраняет последний записанный шаг старой попытки. Старая кнопка подтверждения
показывает сообщение об устаревшей форме. Событие `state_lost` без FSM не
приписывается произвольной прошлой попытке. Новая регистрация получает новый ID;
старая остаётся незавершённой. Нельзя считать её доказанным отказом пользователя.

## Получение отчёта

На скачанной безопасной копии журнала (бот не запускается):

```powershell
python analytics.py "C:\path\journal.analytics.sqlite"
```

Отчёт открывает явно указанный файл в `mode=ro`, не читает `.env`, не создаёт
`Database` и не запускает миграции. Несуществующий путь вызывает ошибку,
а не создание пустой базы.

Пример по игре 50 за 20 октября по Ташкенту:

```powershell
python analytics.py "C:\path\journal.analytics.sqlite" --event-id 50 --from "2026-10-20T00:00:00+05:00" --until "2026-10-21T00:00:00+05:00"
```

`--from` включительно, `--until` (синоним `--to`) исключительно. Дата без времени
означает полночь UTC; timestamp требует часовой пояс. Обратный/пустой интервал,
невалидный ID или дата отклоняются. Без фильтров сохраняется отчёт за всё время.
`--source instagram` дополнительно ограничивает источник.

[`report-event50-example.json`](report-event50-example.json) — воспроизводимый
пример на синтетической базе теста `test_game_interval_metrics_and_all_outcomes`:
1 запуск, 6 начатых форм, 1 завершение и по одной попытке каждого из состояний
unfinished/cancelled/technical_errors/duplicates/superseded. Это не рабочая статистика.

JSON содержит запуски, уникальные аккаунты, отправленные карточки, начала,
завершения и заполненные шаги **за указанный интервал**. `steps` считает уникальные
попытки на шаге, `step_events` — все принятые заполнения с учётом редактирования.
Подтверждённая заявка здесь — сохранённая регистрация (`registration_completed`),
а не ответ о посещении игры и не подтверждение оплаты.

Исходы показываются для попыток, у которых была активность в интервале, с учётом
всей истории до его исключительной верхней границы. Поэтому завершение может
попасть в период без начала, если форма началась раньше. Это отчёт активности,
не когортная конверсия: нельзя делить завершения на начала и называть это конверсией.
Группы взаимно исключаются:

| Поле | Значение |
|---|---|
| `unfinished` | Нет терминального события и последней нерешённой ошибки |
| `cancelled` | Явная отмена формы |
| `superseded` | Форму заменили другой попыткой; отдельно от явного отказа |
| `technical_errors` | Последнее событие — техническая ошибка без последующего восстановления |
| `duplicates` | Последний результат — отказ из-за существующей регистрации |
| `unavailable` | Последний результат — недоступность игры |
| `completed` | Завершённые попытки |

В каждом списке есть последний записанный шаг, последний успешно заполненный
шаг за историю попытки и ожидаемый следующий шаг. `technical_error_events` и
`duplicate_events` отдельно считают события ошибок в интервале, в том числе
ошибки впоследствии успешно завершённых попыток. `unlinked_failures` показывает
ошибки без известной попытки (например, старая кнопка после рестарта). Они не
приписываются пользователю как отдельная брошенная форма. При неизвестной игре
они видны в общем отчёте, а не в отчёте конкретной игры.

Для формы из меню игра определяется по последнему ненулевому `event_id` до конца
периода; её более ранние шаги связываются через `attempt_id`. Будущие выбор игры
или завершение не меняют исторический отчёт с фиксированной верхней границей.
Обычный запуск без игры не приписывается игре по будущим действиям пользователя.
Незавершённость не означает отказ: возможны пауза, потеря FSM и потеря записи журнала.

Внешней панели, таймаутов, автоудаления и периодических рассылок нет. Отчёт
читает историю до конца периода; для большого журнала потребуются оптимизация
и политика хранения. Получать отчёты рекомендуется на копии журнала, чтобы
долгое чтение не мешало записи SQLite.

## Источники трафика

Поддерживаются `event_50` и `event_50_src_instagram` (также `telegram`, `qr`,
`partner`). Источник хранится только из списка `direct`, `menu`, `telegram`,
`instagram`, `qr`, `partner`, `unknown`; произвольный ярлык заменяется `unknown`.
Полный start payload не сохраняется. Формат и длина проверяются.

Примеры: `https://t.me/Razumboy_Bot?start=event_50_src_instagram`,
`https://t.me/Razumboy_Bot?start=event_50_src_qr`.

Запуск и карточка получают источник ссылки. Начало регистрации из карточки
наследует его только при совпадении игры в текущем FSM-контексте. Для другой игры
используется `direct`; для регистрации через меню — `menu`. Источник попытки
фиксируется при начале и сохраняется при редактировании; последующий `/start`
не переименовывает существующую попытку. После потери/очистки FSM контекст источника
может быть утрачен. Это метка ссылки, не проверенная рекламная атрибуция: ссылку
можно переслать. Исторические источники не восстанавливаются догадками.

В отдельный журнал добавляется колонка `source` с `unknown` для старых строк.
Обновление идемпотентно и происходит только при включённой аналитике.
Read-only отчёт читает также формат журнала из `f23d086` без изменения его схемы.

## Безопасное внедрение — только после разрешения

1. Проверить diff и одобрить конкретный коммит. Убедиться, что Railway разворачивает
   только согласованную ветку и сохраняет один worker.
2. До выкладки сделать согласованный SQLite-backup основной БД и сохранить текущую
   рабочую версию. Выбрать время с минимумом активных регистраций: рестарт теряет FSM.
3. На отдельном тестовом окружении проверить старт приложения и маршрутизацию с
   отдельным тестовым ботом, отдельной БД и отключёнными рабочими рассылками.
4. Учесть, что существующий `Database._migrate()` при любом старте приложения
   выполняет свои прежние операции, включая изменение подписок. Этот PR их не
   меняет и не запускает отдельно; перед production-стартом их следует проверить.
5. В согласованное окно выложить одобренный код с аналитикой, оставленной выключенной;
   проверить Railway и одну согласованную тестовую регистрацию.
6. После проверки персистентного Volume и свободного места включить
   `FUNNEL_ANALYTICS_ENABLED=1`. Это потребует управляемого перезапуска. Таблица
   журнала создастся в отдельном файле; миграций бизнес-схемы для аналитики нет.
7. Проверить события, отсутствие личных текстов, дедупликацию и показатели; сверить
   завершения с реальными заявками. Ограничить доступ к журналу и определить срок
   хранения. В версии нет автоматического удаления старых событий.

## Откат

Быстрое отключение: `FUNNEL_ANALYTICS_ENABLED=0` и согласованный перезапуск одного
worker. Это отключает журнал; изменения защиты повторных кнопок остаются.
Полный откат: развернуть предыдущий сохранённый коммит/артефакт и проверить Railway.
Отдельный файл аналитики можно оставить для разбора; удалять его для отката не нужно.
Основную БД не откатывать из старого backup без отдельного решения: это уничтожит
заявки, поступившие после backup. Обратной миграции бизнес-схемы не требуется.

В рамках подготовки ветки деплой, production-миграции и запуск рабочего бота
не выполнялись. Пользовательские локальные изменения вне этой задачи в коммит
не включаются.

Детальный порядок проверки backup/restore и выкладки:
[`railway-analytics-runbook.md`](railway-analytics-runbook.md).
