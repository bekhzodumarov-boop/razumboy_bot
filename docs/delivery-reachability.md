# Доступность пользователей и учёт доставки

Ветка `codex/delivery-reachability` создана от аудита подписчиков `278ac44`.
Рабочие БД, Telegram и Railway при подготовке не использовались. Изменения схемы
исполнялись только в временных тестовых SQLite. Этот документ описывает подготовленную
реализацию и будущую выкладку после разрешения.

## Карта отправок, проверенная до реализации

| Сценарий | Точки отправки | Подход |
|---|---|---|
| Ручные рассылки, шаблоны и анонсы игр | `broadcast_custom_send`, `_do_broadcast` | Общая проверка адресатов, отдельные основная/дополнительная части |
| Изменение/отмена игры, подтверждение участия | `notify_event_change`, `cancel_event_do`, `broadcast_send_dayof` | Доступность отдельно от наличия регистрации |
| Победители и Рандомбой | `winners_broadcast_confirm`, `randoboy_start`, `randoboy_pick_winner` | Общая проверка, в том числе контактов вне users |
| Блиц | `blitz_set_mode`, вложенный `finish_blitz`, `blitz_catch_answer` | Начало, отложенные результаты и первый победитель — отдельные запуски |
| Фотоальбомы | `photo_enter_url` | Общая проверка |
| Автонапоминания перед игрой, в день и повторные | Три функции `auto_remind_*` | Раздельные единицы «игра + адресат»; повторные — только без ответа |
| Розыгрыши по расписанию | `giveaway_announce`, `giveaway_draw`, `giveaway_reminder`, `send_friday_winner_reminders` | Проверка всех выбранных адресатов независимо от исходной таблицы |
| Персональные бонусы, QR и скидки | `common.py`, `_finalize_discount`, `ref_apply_discount_event` | Общий уровень исходящих запросов |
| Ответ организатора пользователю | `reply_to_user_send` | Общий уровень; вывод безопасного кода ошибки |
| Уведомления администраторам, запуск и регистрация | `app.py`, `registration.py`, `user.py`, `common.py`, giveaway/admin | Общий уровень; отделены от результатов массовой рассылки |
| Обычные ответы, фото, документы, CSV | shortcuts `message.answer*` и вызовы `bot.send_*` | Та же Bot-сессия и тот же механизм |
| Публикации в канал/группу | Отрицательные chat ID или username канала | Не превращаются в блокировку личного пользователя |

Во всех массовых сценариях используется `tracked_broadcast` и предварительный
`delivery_recipients`. Индивидуальные отправки наблюдает session middleware,
подключённый сразу после создания Bot в `main()`, до первой отправки и планировщика.
При запуске через собственный код вместо `main()` middleware нужно подключать
явно через `configure_delivery(bot, db)`.

## Модель

Добавляются три таблицы без удаления/перезаписи пользователей, анкет и заявок:

- `user_delivery_state`: контакт, `availability`, `last_successful_send_at` UTC,
  техническая ревизия восстановления доступности;
- `delivery_counters`: суточные UTC-счётчики результатов API без идентификаторов;
- `delivery_runs`: время, фиксированное имя сценария и агрегаты запуска без
  идентификаторов, текстов, телефонов и имён.

Отсутствующая запись статуса означает `unknown`. Это позволяет учитывать
импортированных победителей и других частных адресатов, которых ещё нет в users.
Идентификатор хранится только там, где необходим для проверки доступности;
он не включается в агрегированный отчёт.

`unknown` означает, что доступность не подтверждена, но отправка допустима.
`reachable` устанавливается после успешной отправки, `/start`, разблокировки или
явного выбора «Получать анонсы». Восстановление по входящему событию не заполняет
время успешной отправки: оно обновляется только при успешном send-запросе.
Успех API не означает прочтение сообщения.

Восстановление через `/start`/подписку допускается только в личном чате;
команда в группе не доказывает доступность личных сообщений.

`blocked` устанавливается только при `TelegramForbiddenError`, содержащем
`bot was blocked by the user`, или private `my_chat_member` со статусом `kicked`.
`member` в private-событии восстанавливает доступность. Групповые события игнорируются.
`allowed_updates` приложения определяется Dispatcher, включающим `my_chat_member`.

Категории ошибок: `blocked`, `deactivated`, `forbidden_other`, `rate_limited`,
`network`, `server_error`, `bad_request`, `unknown_error`; отмена запроса — `cancelled`.
Только первая меняет состояние на постоянную блокировку. Даже BadRequest с похожим
текстом не признаётся блокировкой. Автоматический повтор отправки/RetryAfter ожидание
не добавлены: временная ошибка не исключает контакт из следующей рассылки.

Перед каждым частным send состояние проверяется повторно. Это защищает от старого
списка адресатов и блокировки во время предыдущего сообщения. Известному blocked
не отправляется HTTP-запрос; результат обозначается `skipped_blocked`.
Ревизия защищает восстановление после `/start` от пришедшего позже ответа старого
запроса. Успешный параллельный запрос не снимает уже подтверждённую блокировку.

## Подписка

Принудительный `UPDATE ... subscribed=1 WHERE subscribed=0` удалён из `_migrate()`.
Существующие значения сохраняются. Ранее стёртые старой версией отписки автоматически
восстановить нельзя — для этого нужны отдельные доказательства/резервные копии.

`/start` больше не переподписывает существующего пользователя. Разблокировка тоже
не меняет `subscribed`. Явное «Получать анонсы» включает подписку и восстанавливает
доступность. Начальная подписка новых пользователей остаётся прежней; рекламные
согласия или полноценный новый механизм отписки в этом изменении не реализуются.

`get_subscribers()` и список неучастников розыгрыша выбирают только subscribed=1,
не имеющих blocked. Получателей сервисных сообщений капитанам/победителям проверяет
общий фильтр доступности, без применения маркетингового флага к сервисной рассылке.
Списки регистраций для просмотра/экспорта не сокращаются из-за блокировки.

## Метрики

В меню администратора «Подписчики → Доставка рассылок» доступны:

- количество пользователей по unknown/reachable/blocked;
- допущенные подписчики (unknown + reachable, а не гарантированно доставляемые);
- количество других частных контактов вне users;
- число API-попыток и результаты по категориям, накопительно с включения учёта;
- последние пять запусков с раздельными основными и дополнительными результатами.

В `delivery_runs` допущенные адресаты регистрируются до начала отправки. Это
позволяет различить план и попытки при прерывании. Единица учёта — один адресат
для одной игры внутри запуска; для остальных сценариев — адресат внутри запуска.
Повторяющиеся строки входного списка дедуплицируются. Административные итоги,
публикации в канал и команды интерфейса не входят в основные показатели кампании.
Администраторы из переданного списка исключаются из основных метрик, даже если
сами подписаны; их API-запросы видны в общем счётчике.

Некорректные частные адресаты (NULL, ноль, нецелый ID) не отправляются и считаются
отдельно, без признания их блокировкой.

Основная отправка с фото и последующим текстом успешна только при успехе всех
её частей. В API-метриках это два запроса, в итогах кампании — одна попытка.
Сбой дополнительного «Вы уже зарегистрированы» не меняет успех основной отправки:
он попадает в отдельные дополнительные ошибки. Известные пропуски blocked не
считаются API-попытками. Если blocked заранее отфильтрован SQL-выборкой подписчиков,
он отражён в общей доступности, а не как пропуск каждого запуска.

Старая история `broadcasts.sent_count` сохраняется для совместимости; её краткие
старые сообщения не заменяют новый детальный отчёт. Итоги новой массовой отправки
сохраняются даже при ошибке функции, если процесс продолжает выполнять finally.
При аварийном завершении процесса незавершённый итог может потеряться; уже записанные
API-счётчики и доступность остаются. Ровно-однократная доставка не гарантируется.

Статусы и метрики используют небольшие SQLite-записи. Ошибки учёта не прерывают
отправку: фиксируется постоянный код в техническом логе. При недоступности БД
проверка работает как unknown и возможна повторная попытка blocked-контакту;
это ограничение требует мониторинга `delivery_state_or_metrics_write_failed`.
Соединения Database теперь явно закрываются после commit/rollback контекстного
менеджера; это устраняет обнаруженные незакрытые SQLite-соединения при частых вызовах.

## Проверки

Автотесты используют временные БД без восстановления исторических персональных
данных и Bot с OfflineSession без HTTP. Проверены блокировки, все временные и
прочие категории, сообщения/фото/документы, повторный старт и явная подписка,
private block/unblock и игнорирование групп, сохранность subscribed=0 при повторной
инициализации, время успеха, статус победителя вне users, гонка старого ответа,
основная/дополнительная ошибка, частичная составная отправка, реальная логика
розыгрыша и уведомления капитанам, разные игры, конкурентные кампании, прерванная
кампания, агрегатный отчёт/права администратора, ошибка БД и закрытие/rollback соединения.

Результат 20 октября 2026 (Windows): по **73 теста — OK** на Python 3.13.16 и
Python 3.12.14; из них 17 новых тестов доставки. Синтаксис изменённых модулей
проверен Python 3.13, `git diff --check` пройден. Это не live-проверка Linux/Railway
или сети Telegram; она предусмотрена следующим этапом staging после разрешения.

## Безопасное внедрение (не выполнялось)

1. Проверить diff и согласовать конкретный SHA. Ветка не должна автоматически
   деплоиться в production. Зафиксировать текущий рабочий артефакт и один worker.
2. Сделать SQLite Backup API snapshot основной БД и, при наличии, отдельного
   журнала аналитики; проверить `integrity_check` и восстановление в новые тестовые
   файлы. Не копировать live `.db` отдельно от WAL и не печатать персональные данные.
3. На копии проверить повторный запуск новой Database: количество старых записей
   и subscribed=0 не меняются, создаются только дополнительные таблицы доставки.
4. На изолированном staging: отдельный бот, Volume, администраторы, `SCHEDULER_ENABLED=0`.
   Проверить регистрацию, анонс, дополнительные уведомления, блок/разблокировку,
   отписку и повторный `/start`, ручную подписку, перезапуск и отчёт.
5. Подтвердить получение private `my_chat_member`, а также отсутствие реальных
   получателей и каналов в staging. Сетевые ограничения проверить на тестовой сессии;
   не инициировать массовую нагрузку для искусственного получения RetryAfter.
6. После отдельного разрешения в согласованное окно остановить прежний worker,
   выложить одобренную версию, проверить Railway и единственный polling-процесс.
   Новые таблицы создаются при старте. Старые контакты имеют unknown, без выдуманной
   исторической блокировки или времени доставки.
7. Проверить одну согласованную тестовую отправку, запись времени и отчёт. Затем
   постепенно разрешить обычные рассылки; наблюдать SQLite/Volume, задержки и
   ошибки учёта. Назначить срок хранения агрегатов запусков и приватных статусов:
   автоочистки в этой версии нет.

## Откат

При проблеме остановить массовые действия и планировщик (`SCHEDULER_ENABLED=0`),
сохранить snapshot и диагностические агрегаты. Ручные рассылки этим флагом не
отключаются — временно не использовать их.

Не возвращать старую версию без подготовки: её `_migrate()` снова включит отписки,
`/start` переподпишет пользователя, а рассылки перестанут учитывать blocked.
Для отката нужен согласованный совместимый артефакт, сохраняющий удаление принудительной
переподписки и фильтрацию доступности. Новые таблицы можно оставить; удалять их
или восстанавливать старую БД поверх новых заявок не требуется. Любое восстановление
backup поверх актуальных данных — отдельное решение с переносом новых регистраций.

Ограничения: нет новых рекламных согласий, общей транзакции между Telegram и SQLite,
межпроцессной очереди и распределённого ограничения скорости. Архитектура рассчитана
на один worker. Успешный Telegram API-ответ не подтверждает прочтение.
